# 依存ライブラリの更新とセキュリティの運用方針

- 状態: **合意済み・導入中** 2026-11-05
- 目的: 脆弱性の報告や修正版の公開に、すぐ・安全に追いつく。自動テストで確かめられる更新は自動で入れ、それ以外は Claude が一次解析してから、持ち主が判断する

---

## 1. 全体の流れ

```
脆弱性の報告・新しい版の公開
        │
        ▼
Dependabot が更新のPRを作る（脆弱性の修正はすぐ、ふつうの更新は週1回）
        │
        ▼
自動チェック：型チェック／ルールのテスト／画面の通しテスト／ビルド／npm audit
        │
   ┌────┴─────────────────────┐
   ▼                           ▼
【小】自動マージ → 公開       【中・大】または チェック失敗
                              → 毎朝、Claude が一次解析して PR にコメント
                              → 持ち主が確認してマージ
                                （実装の変更や判断が要るものは issue を起票）
```

---

## 2. 更新の大きさの分け方

| 区分 | 対象 | 扱い |
|---|---|---|
| **小** | 開発用の道具（vite, vitest, typescript, @types/* など）の patch・minor／ゲームで使うライブラリの patch／GitHub Actions の部品の patch・minor／上の範囲に収まる脆弱性の修正 | 自動チェックが全部通れば、**自動でマージ**して公開する |
| **中** | ゲームで使うライブラリ（react, react-dom, peerjs, howler, motion, @dnd-kit/*, zustand, canvas-confetti, @fontsource/*）の minor | **一次解析 → 報告 → 持ち主がマージ** |
| **大** | major（互換性がなくなる可能性がある）すべて | **一次解析 → 報告 → 持ち主がマージ**。移行の作業が要るなら issue を起票し、仕様書と同じく手順を書いてから進める |
| **チェック失敗** | 区分にかかわらず、自動チェックが1つでも落ちたもの | **一次解析**（なぜ落ちたか、直し方）→ 報告 |

- 区分は「semver（版番号の付け方の決まり）」と、依存がゲーム本体用か開発用かで機械的に決める
- 脆弱性の修正でも、中・大に当たるものは自動マージしない。深刻度が高いものは、解析の報告で「すぐマージを推奨」と明記する

---

## 3. 自動チェック（マージ前のハーネス）

| チェック | 目的 | 状態 |
|---|---|---|
| 型チェック（`tsc`） | 型の食い違い | 実装済み |
| ルールのテスト・シミュレーション・楽譜のテスト（`npm test`） | ゲームのルールと内蔵BGMが壊れていないか | 実装済み |
| ビルド | 公開できる形にまとまるか | 実装済み |
| **画面の通しテスト（Playwright）** | ブラウザ2つで、部屋を作る → 参加 → ドラッグ・タップで並べる → 予想 → 答え合わせ → 結果 → ロビーまで自動で遊ぶ。React などを上げても画面が動くかを確かめる。つなぐためのサーバー（`peer`）を CI の中に立て、外のサーバーに頼らない（`e2e/`） | 実装済み |
| `npm audit`（深刻度 high 以上） | 既知の脆弱性が残っていないか | 実装済み |

「自動テストで担保できる」と言えるのは、上の全部が通ったときだけとする。

## 4. Dependabot の設定

| 項目 | 設定 |
|---|---|
| 対象 | npm、GitHub Actions |
| 頻度 | 週1回（月曜の朝）。脆弱性の修正は見つかりしだい |
| まとめ方 | 「React 系」「ビルド・テストの道具」「その他」にまとめて、PR の数を抑える |
| 待ち期間（cooldown） | 公開から **3日たった版**だけを候補にする（乗っ取られたパッケージの悪い版は、公開直後に見つかって取り下げられることが多いため）。脆弱性の修正は待たない |
| 同時に開くPRの上限 | 5件 |

リポジトリの設定で、あわせて次を有効にする：Dependabot alerts、Dependabot security updates、シークレットスキャン、自動マージの許可。

---

## 5. main のルール

- 「チェックが全部通るまでマージさせない」ルールを main に付ける（必須にするチェックは deploy の `check`）（自動マージが、チェックを待ってからマージするようにするため）
- **持ち主（chris949）は対象外**。持ち主の直接 push は今までどおりできる（Claude の push も持ち主のアカウントで行う）
- 書き込めるのは持ち主だけなので、第三者は push もマージもできない（フォークからの PR は、持ち主がマージしない限り入らない）

---

## 6. 一次解析（毎朝の定期実行）

Claude の定期実行で、毎朝1回、次を行う。リポジトリに API キーは置かない。

1. 開いている Dependabot の PR と、Dependabot alerts を確かめる
2. 中・大、またはチェックが落ちた PR ごとに解析する
   - 変更履歴・リリースノートから、互換性のない変更を拾う
   - このゲームのどのコードが使っている機能か（影響範囲）
   - 脆弱性なら、深刻度と、このゲームで実際に狙える条件がそろうか
   - チェックが落ちていれば、原因と直し方
   - おすすめ：「すぐマージ」「直してからマージ」「見送り」
3. 結果を **その PR にコメント**し、持ち主をレビュー担当にする
4. 実装の変更や、仕様の判断が要るものは **issue を起票**する（PR から issue へリンクする）
5. 何もなければ、何もしない（コメントもしない）

---

## 7. 仕組みの置き場所

| 仕組み | 場所 |
|---|---|
| チェックと公開 | `.github/workflows/deploy.yml`（PR・push・1時間ごと。自動マージは push のきっかけにならないため、1時間ごとに未公開の更新を見に行く） |
| Dependabot の設定 | `.github/dependabot.yml` |
| 区分けと自動マージ | `.github/workflows/dependabot-automerge.yml`（小は自動マージを予約し「自動マージ」ラベル、中・大は「要解析」ラベルと担当） |
| 画面の通しテスト | `e2e/`、`playwright.config.ts`。手元では `npm run build && npm run e2e` |

## 8. 決めておくこと

| # | 論点 | 案 |
|---|---|---|
| D1 | 定期実行を動かす場所 | クラウドの定期実行（Mac が閉じていても動く）。GitHub へのアクセス権限の設定が要る |
| D2 | 自動マージした更新の知らせ | 不要（GitHub の通知で十分）。週1回、まとめて一覧を PR コメントか issue にするかは運用しながら決める |
| D3 | 画面の通しテストが不安定になったとき | 同じテストを1回だけやり直す。それでも落ちたら「チェック失敗」として一次解析に回す |
